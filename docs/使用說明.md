# POS 數據分析系統 — 使用說明書

本文件為**內部操作手冊**，供實際使用本系統的人員依步驟執行。若需專案技術說明與架構，請參閱專案根目錄的 `README.md`。

---

## 一、前置準備

### 1. 安裝環境

- 建議使用 **Python 3.11 + venv**，在專案根目錄（與 `pos_system_v2.py` 同一層）開啟終端機，執行：

  ```bash
  python -m venv .venv
  # Windows: .venv\Scripts\activate
  # macOS/Linux: source .venv/bin/activate
  pip install -r requirements.txt
  ```

- 若只要跑公開離線 Demo，改安裝：

  ```bash
  pip install -r requirements-demo.txt
  ```

- 若要跑 v3 analytics 的 X/Y Prophet，先完成正式環境安裝後再加裝：

  ```bash
  pip install -r requirements-forecast.txt
  ```

  NeuralProphet 實驗環境請改用獨立 venv + `requirements-neuralprophet.txt`，不要與正式 NumPy 2.x 混裝。
- 既有內部機器若已使用 Conda，也可繼續依 `environment.yml` 建立/啟用環境：

  ```bash
  conda env create -f environment.yml
  conda activate <env-name>
  ```

### 2. 設定資料庫連線

- 在專案根目錄建立 **`.env`** 檔案（若尚未建立）。
- 填入 POS SQL Server 的連線資訊，格式如下：

  ```
  DB_DRIVER={ODBC Driver 17 for SQL Server}
  DB_SERVER=你的伺服器位址
  DB_DATABASE=你的資料庫名稱
  DB_UID=你的帳號
  DB_PWD=你的密碼
  DB_TRUST_CERT=yes
  ```

- 請確認可從本機連線至 POS 資料庫（防火牆、VPN、權限等）。

### 3. 第一次執行前檢查

- 專案根目錄下會有 `data/` 資料夾；若無，執行主程式後會自動建立。
- 不需手動建立 `data/processed/` 或 `data/insights/`，程式會自動建立。

## 二、日常使用：資料同步（必做）

**目的**：從 POS 抓取「今日庫存」與「銷售歷史」，寫入本機快取，供後續分析與預測使用。

**指令**：

```bash
python pos_system_v2.py
```

**執行後會發生的事**：

- 連線至 POS 資料庫。
- 產生資料字典 → `data/processed/table_structure.txt`。
- 抓取商品庫存主檔 → 寫入 **`data/processed/DetailGoodsStockToday.csv`**。
- 增量同步銷售紀錄 → 寫入 **`data/processed/sales_daily_parquet/`**（第一次可能為全量同步，較久）。

**建議**：排程或每日固定執行一次，確保本地資料為最新，再跑底下的分析或預測。

**若出現「無法連線至 POS 伺服器」**：請檢查 `.env`、網路、VPN 與資料庫權限。

## 二之一、Firebase 同步（v3 daily job）

**目的**：從 POS 抓取今日庫存，上傳 Firestore `products` / `replenishment`（內容 hash 存在 `sync_state`，未變動則跳過寫入）。

**本機指令**：

```powershell
python -m pos_pipeline.cli daily
```

**雲端**：Cloud Run Job `pos-pipeline-daily`，排程約 09:00–19:00 每 2 小時一次。部署與祕密說明見 **[CLOUD_RUN_DAILY.md](CLOUD_RUN_DAILY.md)**。

**尚未包含**：`inbound_movements` 仍走下方舊工具；App 顯示上次同步時間尚未實作。

## 二之一（舊）、Firebase 同步（POS_Sync_Tool）

**目的**：從 POS 資料庫抓取商品主檔，經加工後上傳至 Firebase Firestore，供前端或內部系統使用。目前仍負責 **入貨紀錄** 增量同步。

**前提**：專案根目錄需有 **`serviceAccountKey.json`**（Firebase 服務帳號金鑰），且 `.env` 可連線至 POS 資料庫。

**指令**：

```bash
python POS_Sync_Tool.py
```

**執行後會發生的事**：

1. 連線至 POS 資料庫，抓取商品庫存主檔（同 `get_stock_master_data()`）。
2. **上傳至 Firestore `products` collection**：僅含基本資訊（ProductCode, Barcode, Name, CurrStock, RetailPrice, Category, Supplier），供對外或一般查詢使用。
3. **加工並上傳至 Firestore `replenishment` collection**：經 `replenishment_service.prepare()` 解析 Note（FirstOrderQty、NoteDescription），並寫入 LastInCost, AvgCost, InboundLocation, FirstOrderQty, NoteDescription 等補貨建議用欄位；此 collection 建議僅供內部補貨決策使用。
4. **增量同步入貨紀錄至 Firestore `inbound_movements` collection**：以 SID watermark 增量讀取最近 14 天入貨紀錄，供 App/Admin 進行「單據 vs 實際到貨」核對使用。

**Firestore 兩大 collection 對照**：

| Collection      | 用途說明           | 主要欄位（示意） |
|-----------------|--------------------|------------------|
| `products`      | 商品基本資訊       | ProductCode, Name, CurrStock, RetailPrice, Category, Supplier |
| `replenishment` | 補貨建議用敏感資訊 | ProductCode, LastInCost, AvgCost, InboundLocation, FirstOrderQty, NoteDescription, guessed_min, guessed_multiple（後兩者由 update_min_multiple.py 寫入） |
| `inbound_movements` | 系統單據入貨紀錄（增量） | SID、BillDate、ProductType2Name1（供應商）、GoodsNo（= productCode）、OriQty、ChQty、NewQty 等 |

**設計說明**：為何拆成兩個 collection、如何設定兩套獨立安全規則以兼顧前端效能與敏感資料保護，請見 **[Firestore_雙Collection設計與安全說明.md](Firestore_雙Collection設計與安全說明.md)**。專案演進與架構決策脈絡（客戶端計算、權限隔離、冷啟動與人機協作）見 **[專案心路歷程與架構決策.md](專案心路歷程與架構決策.md)**。

**若出現「無法連線至 POS 伺服器」**：同 **二、資料同步**，請檢查 `.env` 與網路。**若 Firebase 上傳失敗**：請確認 `serviceAccountKey.json` 路徑與權限。

## 二之三、入貨紀錄增量同步與 Admin 核對

**目的**：從 POS 入貨紀錄（`GoodsStockMovement`，`MoveTypeID=1`）增量同步到 Firebase `inbound_movements` collection，供 App/Admin 核對「系統單據 ChQty」與「實際到貨 arrivalQty」是否吻合。

**前提**：同 **二之一**（可連線至 POS 資料庫、有 `serviceAccountKey.json`）。本步驟已整合在 `POS_Sync_Tool.py` 的同步流程中，執行 `python POS_Sync_Tool.py` 時會自動執行。

**執行後會發生的事**：
1. 從 `data/cache/sync_cache.json` 讀取 watermark（`inbound_last_sid`），預設為 0。
2. 查詢 `GoodsStockMovement` 中 `SID > last_sid` 且 `BillDate >= 最近 14 天` 的入貨紀錄。
3. 增量上傳至 Firestore `inbound_movements`（doc ID = SID），使用 hash 快取只寫入有變動的 document。
4. 更新 `data/cache/sync_cache.json` 中的 `inbound_last_sid`。

**欄位**：SID、BillDate、GoodsNo（= productCode）、Barcode、GoodsName1、OriQty、ChQty、NewQty、ProductType2Name1（供應商）、invNo、Note、syncedAt。

**Admin 比對規則（建議，由 App 端實作）**：
- 配對 key：`GoodsNo`（inbound） == `productCode`（arrivalHistory）
- 系統數量：`inbound_movements.ChQty`
- 實際數量：同一商品的 `SUM(arrivalHistory.arrivalQty)`（可能多次掃碼需累加）
- 容忍時間差：`arrivalHistory.createdAt` 落在 `BillDate ± 7 天` 視為同一批到貨。

## 二之二、Min/Multiple 更新（update_min_multiple）

**目的**：從 POS 入貨紀錄（MoveTypeID=1）計算每個商品的 **guessed_min**（最低起訂量）與 **guessed_multiple**（下單倍數），並僅將這兩個欄位寫入 Firestore **replenishment** collection，供人機協作（前端贊同／修改）使用。可獨立排程，不需與 POS_Sync_Tool 同跑。

**前提**：可連線至 POS 資料庫、專案根目錄有 **`serviceAccountKey.json`**。建議先至少執行一次 **二之一、Firebase 同步**，讓 replenishment 已有基本 document，再跑本腳本補上 guessed_min／guessed_multiple。

**指令**：

```bash
python update_min_multiple.py
```

**執行後會發生的事**：

1. 連線至 POS 資料庫，查詢最近 **2 年**入貨紀錄（GoodsNo, ChQty, BillDate）。
2. 依商品（GoodsNo = ProductCode）以**因數統計法**計算 guessed_min、guessed_multiple。
3. 僅將 **guessed_min**、**guessed_multiple** 寫入 Firestore `replenishment`（merge=True，不覆蓋其他欄位）；有 hash 快取，只更新有變動的 document。

**排程建議**：可每週或每月執行一次，與每日庫存同步（POS_Sync_Tool）分開。

**若出現「無法連線至 POS 伺服器」**：同 **二、資料同步**。**若 Firebase 上傳失敗**：請確認 `serviceAccountKey.json`。

## 三、進階：ABC/XYZ + 目標庫存（v3 analytics）

**目的**：商品分級（A/B/C/New、X/Y/Z）與 A/B/New/C 目標庫存規劃。

**前提**：需能連 POS，且專案根目錄有 **`serviceAccountKey.json`**（或設定 `FIREBASE_KEY_PATH`）。完整 CLI 會自行更新庫存 CSV 與銷售 Parquet，並上傳結果欄位至 Firestore。

**指令**：

```bash
pip install -r requirements-forecast.txt   # X/Y 使用 Prophet 時需要
python -m pos_pipeline.cli analytics
```

可選環境變數：`FORECAST_BACKEND=prophet|neuralprophet|recent_3m`（預設 `prophet`）。

**輸出**：

- **`data/insights/abc_xyz_analysis.csv`**：ABC/XYZ 與策略標籤
- **`data/insights/target_stock_plan.csv`**：A/B/New/C 目標庫存（精簡欄位）
- **`data/insights/target_stock_trace.csv`**：計算追蹤（模型、季節、上限等）
- **Firestore**：`products` / `replenishment` merge 寫入 `ABC_Class`、`XYZ_Class`、`note`；`replenishment` 另寫入整數 `Target_Stock`

規格與流程圖：[`ANALYTICS_PIPELINE.md`](ANALYTICS_PIPELINE.md)。

**與 Web App 補貨頁的關係**：

- 管理端補貨建議詳情中的「**備註 (note)**」來自 Firestore `replenishment.note`（由 analytics 上傳 POS `Note`）。
- **`NoteDescription`**、**`FirstOrderQty`** 需執行 daily／`POS_Sync_Tool.py` 解析 `Note` 後才會寫入 `replenishment`。
- Web App 經 **`GET /api/forecast`** 讀取並顯示。

## 五、建議執行順序（總整理）

1. **第一次**：完成 **一、前置準備** → 執行 daily／資料同步 → 視需求執行 **三、v3 analytics**。
2. **之後每次要預測或報表前**：先同步庫存與銷售，再執行 **三**。
3. 僅要「庫存與銷售資料更新」時，只執行 daily／資料同步即可。
4. **若要更新 Firebase 庫存／入貨**：執行 daily（v3）或過渡的 `POS_Sync_Tool.py`；**ABC/XYZ 與 Target_Stock** 由 **三、v3 analytics** 上傳。
5. **若要更新 replenishment 的 guessed_min／guessed_multiple**：執行 **二之二、Min/Multiple 更新**（`python update_min_multiple.py`）；可獨立排程（如每週一次），不一定要與 POS_Sync_Tool 同跑。
6. 規則與流程圖：[`ANALYTICS_PIPELINE.md`](ANALYTICS_PIPELINE.md)。
