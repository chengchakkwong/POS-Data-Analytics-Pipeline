# POS 數據分析系統 — 使用說明書

本文件為**內部操作手冊**，供實際使用本系統的人員依步驟執行。若需專案技術說明與架構，請參閱專案根目錄的 `README.md`。

正式入口一律使用 v3 CLI：`python -m pos_pipeline.cli …`。舊的 `POS_Sync_Tool.py`／`pos_system_v2.py`／`update_min_multiple.py` 等根目錄腳本已移除。

---

## 一、前置準備

### 1. 安裝環境

- 建議使用 **Python 3.11 + venv**，在專案根目錄開啟終端機，執行：

  ```bash
  python -m venv .venv
  # Windows: .venv\Scripts\activate
  # macOS/Linux: source .venv/bin/activate
  pip install -r requirements/prod.txt
  pip install -e .
  ```

- 若只要跑公開離線 Demo，改安裝：

  ```bash
  pip install -r requirements/demo.txt
  pip install -e .
  ```

- 若要跑 v3 analytics 的 X/Y Prophet，先完成正式環境安裝後再加裝：

  ```bash
  pip install -r requirements/forecast.txt
  ```

  NeuralProphet 實驗環境請改用獨立 venv + `requirements/neuralprophet.txt`，不要與正式 NumPy 2.x 混裝。
### 2. 設定資料庫連線

- 在專案根目錄建立 **`.env`** 檔案（若尚未建立）。
- 填入 POS SQL Server 的連線資訊，格式如下：

  ```
  DB_DRIVER={ODBC Driver 17 for SQL Server}
  DB_SERVER=你的伺服器位址
  DB_DATABASE=你的資料庫名稱
  DB_UID=你的帳號
  DB_PWD=你的密碼
  DB_TRUST_CERT=yes
  ```

- 請確認可從本機連線至 POS 資料庫（防火牆、VPN、權限等）。

### 3. Firebase（daily／analytics／min-multiple 上傳時需要）

- 專案根目錄需有 **`serviceAccountKey.json`**，或設定環境變數 **`FIREBASE_KEY_PATH`**。

### 4. 第一次執行前檢查

- 專案根目錄下會有 `data/` 資料夾；若無，執行主程式後會自動建立。
- 不需手動建立 `data/processed/` 或 `data/insights/`，程式會自動建立。

## 二、日常使用：Firebase 同步（v3 daily）

**目的**：從 POS 抓取今日庫存，寫入本機 CSV，並上傳 Firestore：

- `products`／`replenishment`（內容 hash 在 `sync_state`，未變動則跳過寫入）
- `inbound_movements`（SID watermark + 近 14 天；watermark 在 `sync_state/inbound_movements`）

**本機指令**：

```powershell
python -m pos_pipeline.cli daily
```

**雲端**：Cloud Run Job `pos-pipeline-daily`，排程約 09:00–19:00 每 2 小時一次。部署與祕密說明見 **[CLOUD_RUN_DAILY.md](CLOUD_RUN_DAILY.md)**。

**本機產出**：`data/processed/DetailGoodsStockToday.csv`。

**Firestore collection 對照（示意）**：

| Collection | 用途 | 主要欄位（示意） |
|------------|------|------------------|
| `products` | 商品基本資訊 | ProductCode, Name, CurrStock, RetailPrice, Category, Supplier |
| `replenishment` | 補貨用敏感／規劃欄位 | LastInCost, AvgCost, FirstOrderQty, NoteDescription, guessed_min, guessed_multiple, Target_Stock, ABC/XYZ 等 |
| `inbound_movements` | 系統入貨單據（增量） | SID, BillDate, GoodsNo, ChQty, OriQty, NewQty 等 |

**設計說明**：雙 collection 權限與資料流見 **[Firestore_雙Collection設計與安全說明.md](Firestore_雙Collection設計與安全說明.md)**；架構決策見 **[專案心路歷程與架構決策.md](專案心路歷程與架構決策.md)**。

**尚未實作**：App 顯示「上次同步時間」（`lastSyncedAt`）。

**若出現「無法連線至 POS 伺服器」**：請檢查 `.env`、網路、VPN 與資料庫權限。**若 Firebase 上傳失敗**：請確認金鑰路徑與權限。

## 二之一、入貨核對（Admin）

**目的**：以 `inbound_movements`（系統單據）對照 App 的 `arrivalHistory`（實際到貨），供 Admin 紅綠燈核對。資料由 **二、daily** 增量同步，不必另跑腳本。

**Admin 比對規則（建議，由 App 端實作）**：

- 配對 key：`GoodsNo`（inbound） == `productCode`（arrivalHistory）
- 系統數量：`inbound_movements.ChQty`
- 實際數量：同一商品的 `SUM(arrivalHistory.arrivalQty)`
- 容忍時間差：`arrivalHistory.createdAt` 落在 `BillDate ± 7 天`

## 二之二、Min/Multiple 更新（v3）

**目的**：從近 2 年入貨 `ChQty` 推算 **guessed_min**／**guessed_multiple**，merge 進 `replenishment`（不覆寫人工 `MinOrderQty`／`OrderMultiple`）。與 daily／analytics **分開排程**。

**指令**：

```powershell
python -m pos_pipeline.cli min-multiple
# 可選：python -m pos_pipeline.cli min-multiple --years 2
```

**執行後會發生的事**：

1. 查詢 `MoveTypeID=1` 且 `ChQty > 0` 的入貨歷史。
2. 依 GoodsNo（= ProductCode）以因數統計法計算 guess。
3. 只寫入 `guessed_min`／`guessed_multiple`；指紋在 `sync_state/min_multiple`。

**排程建議**：每週一次，或與 analytics 同日先後跑（先 analytics 再 min-multiple）；不要塞進每 2 小時的 daily。

## 三、進階：ABC/XYZ + 目標庫存（v3 analytics）

**目的**：商品分級（A/B/C/New、X/Y/Z）與 A/B/New/C 目標庫存規劃；會自行更新庫存 CSV、增量銷售 Parquet，並上傳結果欄位。

**指令**：

```powershell
pip install -r requirements/forecast.txt   # X/Y 使用 Prophet 時需要
python -m pos_pipeline.cli analytics
```

可選環境變數：`FORECAST_BACKEND=prophet|neuralprophet|recent_3m`（預設 `prophet`）。

**輸出**：

- **`data/insights/abc_xyz_analysis.csv`**：ABC/XYZ 與策略標籤
- **`data/insights/target_stock_plan.csv`**：目標庫存（精簡欄位）
- **`data/insights/target_stock_trace.csv`**：計算追蹤
- **Firestore**：`ABC_Class`／`XYZ_Class`／`note`；`replenishment` 另寫整數 `Target_Stock`

規格：[`ANALYTICS_PIPELINE.md`](ANALYTICS_PIPELINE.md)。

**與 Web App 補貨頁**：

- 「備註 (note)」來自 analytics 上傳的 `replenishment.note`（POS `Note`）。
- **`NoteDescription`**、**`FirstOrderQty`** 由 **daily** 解析 `Note` 後寫入。
- Web App 經 **`GET /api/forecast`** 讀取。

## 五、建議執行順序（總整理）

1. **第一次**：完成 **一、前置準備** → `cli daily` → 視需求 `cli analytics`／`cli min-multiple`。
2. **之後每次要預測前**：可先 `daily`，再跑 **三、analytics**（analytics 本身也會更新庫存與銷售快取）。
3. **營業時段庫存／入貨上雲**：靠 Cloud Run `daily`（或本機 `cli daily`）。
4. **guessed_min／guessed_multiple**：`cli min-multiple`（獨立排程）。
5. 規則與流程圖：[`ANALYTICS_PIPELINE.md`](ANALYTICS_PIPELINE.md)。
